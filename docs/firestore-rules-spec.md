# Firestore / Storage Security Rules ve İndeks Spesifikasyonu

> **Sözleşmedir.** Kaynak: `docs/domain-model.md` (şema, yetki matrisi §3, durum makinesi §5, sayaçlar §4). Claude Code `firebase/firestore.rules`, `firebase/storage.rules`, `firebase/firestore.indexes.json` dosyalarını **bu belgeye göre** yazar ve emülatör testleriyle kanıtlar (`docs/testing.md §6`).
> Buradaki kod blokları **tasarım taslağıdır** (sözdizimi emülatörde doğrulanır); davranış ve kural listesi bağlayıcıdır. Çelişki/boşlukta `AskUserQuestion` ile sor.

## 1. İlkeler

1. **Varsayılan ret.** Açıkça izin verilmeyen her şey reddedilir. Son kural: `match /{document=**} { allow read, write: if false; }`.
2. **`allow delete: if false` her koleksiyonda ve her alt koleksiyonda — süper admin dahil** (D-10). Alan düzeyinde silme (`FieldValue.delete()`, `arrayRemove`) bir *update*'tir ve izinli alan listesindeyse serbesttir.
3. **Yetki Rules'ta uygulanır**, arayüzde gizlemek yetmez (CLAUDE.md §9). Her yeni yazma yolu **aynı commit'te** Rules + indeks + Rules testi içerir.
4. **Beyaz liste (allow-list) alan kontrolü:** her `create`/`update` izinli alan kümesini `hasOnly([...])` ile sınırlar; `diff().affectedKeys()` kullanılır. Bilinmeyen alan = ret.
5. **Sunucu zamanı:** `createdAt/updatedAt/deletedAt` değerleri `request.time`'a eşit olmalıdır (istemci `FieldValue.serverTimestamp()` yazar).
6. **Tip ve sınır doğrulaması:** `is string`, `size()` aralıkları, `in [...]` numaralandırmaları — `Limits` sabitleriyle (domain-model §9) **aynı** sayılar. Parite testi: `tool/` altında Rules metnindeki sayılar ile `Limits` karşılaştırılır (`docs/testing.md §6`, madde 11).
7. **Rules filtre değildir.** Liste sorgusu, kuralın koşulunu **kanıtlayabilmek** için gereken `where` süzgeçlerini taşımak zorundadır (§6 Sorgu sözleşmesi). Aksi halde `permission-denied`.
8. **Erişim çağrısı bütçesi:** tek işlem başına en çok 10, tek istek (batch/transaction) toplamında en çok 20 `get/exists/getAfter`. Kurallar bu yüzden **az sayıda belgeye** bakar (kullanıcı belgesi, o kulübün üyelik belgesi, kulüp belgesi). Aynı belgeye tekrar bakmak tek sayılıyorsa bile bütçe **emülatörde ölçülür**; hesap silme gibi çok işlemli akışlar **parçalara bölünür** (≤ 5 üyelik/parça — T-29 ölçümü `budget/account_deletion_result.json`: üyelik parçası `1 + 2N` tekil yol, N = 9 geçer, N = 10 `Service call error`; `Limits.accountDeletionChunk` = 5, RP06). Bütçe aşımı bir tasarım hatasıdır, kuralı gevşetmek değil işlemi bölmek çözümdür.
9. Süper admin **yalnızca claim**: `request.auth.token.superadmin == true` (D-28). Firestore alanı yetki vermez.
10. E-posta alan adı kısıtı **Rules'ta da** (D-27): `request.auth.token.email_verified == true` ve `email.lower().matches('.*@(ogr\\.gumushane\\.edu\\.tr|gumushane\\.edu\\.tr|gmail\\.com)')`. Alan adı listesi `ALLOWED_EMAIL_DOMAINS` ile aynı; parite testi zorunlu.
    > **GEÇİCİ (kullanıcı kararı 2026-10-13 · K-M, CD-136 · borç W-61):** test süresince desende `gmail\\.com` de vardır (`EmailDomainPolicy.temporaryTestDomains`). Kalıcı liste yalnızca iki üniversite alan adıdır (`ALLOWED_EMAIL_DOMAINS`, `EmailDomainPolicy.universityDomains`); `gmail\\.com` teslimden önce (T-45) desenden çıkarılır ve kurallar yeniden yüklenir.

## 2. Yardımcı fonksiyonlar (taslak)

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // ---- kimlik ----
    function signedIn()   { return request.auth != null; }
    function uid()        { return request.auth.uid; }
    function isSuper()    { return signedIn() && request.auth.token.get('superadmin', false) == true; }
    // GEÇİCİ (test): gmail.com — W-61, teslimden önce kaldırılır
    function emailOk()    { return signedIn() && request.auth.token.email_verified == true
                              && request.auth.token.email.lower().matches('.*@(ogr\\.gumushane\\.edu\\.tr|gumushane\\.edu\\.tr|gmail\\.com)'); }
    function userPath(id) { return /databases/$(database)/documents/users/$(id); }
    function me()         { return get(userPath(uid())).data; }
    // aktif = e-posta doğrulanmış + kullanıcı belgesi var + askıda/silinmiş değil + profil tamam
    function activeUser() { return emailOk() && exists(userPath(uid())) && me().status == 'active' && me().profileComplete == true; }
    // hesap silme (T-29): silinmiş hesabın sahibi — yalnızca temizlik dalları (M14, contact, blocks/savedPosts soft delete)
    function deletedUser()    { return emailOk() && get(userPath(uid())).data.status == 'deleted'; }
    // activeUser() istemeyen sahip dalları (settings, private/account, üyelik günlüğü): silinmiş hesap yazamaz
    function notDeletedUser() { return !exists(userPath(uid())) || me().status != 'deleted'; }

    // ---- üyelik ----
    function mPath(c, u)  { return /databases/$(database)/documents/memberships/$(c + '_' + u); }
    function hasM(c)      { return exists(mPath(c, uid())); }
    function myM(c)       { return get(mPath(c, uid())).data; }
    function mActive(c)   { return hasM(c) && myM(c).status == 'active'; }
    function isMember(c)  { return mActive(c) && myM(c).role in ['member','board','president']; }   // yazma yetkili üye
    function isManager(c) { return mActive(c) && myM(c).role in ['board','president']; }
    function isPres(c)    { return mActive(c) && myM(c).role == 'president'; }
    function isAdvisor(c) { return mActive(c) && myM(c).role == 'advisor'; }
    // Okuma kapıları: ikisi de emailOk() ister (doğrulamasını / alan adını yitiren jeton okuyamaz — CD-137 madde 8r)
    function seesInside(c){ return emailOk() && (isSuper() || mActive(c)); }  // gönderi, üye listesi, members-only etkinlik; askıdaki üye OKUR
    // panel (danışman salt okunur): yönetici / danışmanın hesabı AKTİF olmalı — askıdaki yönetici başvuru, contact ve günlüğü okuyamaz
    function seesMgmt(c)  { return emailOk() && (isSuper() || (activeUser() && (isManager(c) || isAdvisor(c)))); }

    // ---- ortak alanlar ----
    function baseCreate() {
      return request.resource.data.createdAt == request.time && request.resource.data.updatedAt == request.time
          && request.resource.data.isDeleted == false
          && request.resource.data.get('deletedAt', null) == null && request.resource.data.get('deletedBy', null) == null;
    }
    function touches(keys) { return request.resource.data.diff(resource.data).affectedKeys().hasOnly(keys.concat(['updatedAt']))
                                  && request.resource.data.updatedAt == request.time; }
    function isSoftDelete(extra) {
      return resource.data.isDeleted == false && request.resource.data.isDeleted == true
          && request.resource.data.deletedBy == uid() && request.resource.data.deletedAt == request.time
          && touches(['isDeleted','deletedAt','deletedBy'].concat(extra));
    }
    function isRestore(extra) {
      return resource.data.isDeleted == true && request.resource.data.isDeleted == false
          && request.resource.data.deletedAt == null && request.resource.data.deletedBy == null
          && touches(['isDeleted','deletedAt','deletedBy'].concat(extra));
    }
    // delta doğrulama (±1) — `getAfter` ile aynı batch içindeki yazımı görür
    function counterDelta(path, field, d) { return getAfter(path).data[field] == get(path).data[field] + d; }
  }
}
```
- `softDelete`/`restore` kimin yapabileceği **koleksiyona özeldir** (§4); `isSoftDelete` yalnızca biçimi doğrular.
- `restore` yalnızca silmeyi yapan (`resource.data.deletedBy == uid()`) ya da süper admin tarafından yapılır (Geri al toast'ı).

## 3. Koleksiyon kuralları

Gösterim: **R** okuma (get/list), **C** create, **U** update, **D** delete (hep `false`). "Aktif" = `activeUser()`.

### 3.1 `users/{uid}`
- **R:** `emailOk()` (doğrulanmış herhangi bir kullanıcı). `isDeleted` süzgeci **yok**: hesabı silinmiş (anonimleştirilmiş, `status=='deleted'`) kullanıcı belgesi de okunur; böylece gönderi/yorum yazarı "Silinmiş kullanıcı" olarak gösterilebilir. Liste sorguları (ADM-05) `isDeleted==false` ekler.
- **C:** `uid == request.auth.uid`, `emailOk()`, belge yok; `status=='active'`, `profileComplete==false`, `staff==false`, `isDeleted==false`; alan beyaz listesi; `name` 2–60. **`private/account` ile birlikte oluşur:** `existsAfter(users/{uid}/private/account)` (aynı batch — `createProfile`); hesap belgesi olmayan profil oluşturulamaz (aksi halde T-37 askıya alma batch'i `not-found` ile düşer — CD-133 madde 14).
- **U (sahibi):** `name, avatarSeed, avatarPath, department, year, interests, bio, profileComplete` (+`updatedAt`); `interests.size()` 1–5; `bio.size() <= 140`. **Biçim (C ve U; CD-133 madde 14):** `name` / `nameLower` alt sınırı kırpılmış metinde (`trim().size() >= 2`); `avatarSeed.size() <= 64` (`// limit: avatarSeedMax`); `avatarPath` = `users/{uid}/` + `StoragePaths.fileNamePattern`. **`profileComplete`:** `true` yalnızca birleşmiş belgede `department` (öğrencide ayrıca `year`) doluyken (AUT-05 zorunlu alanları); `true → false` yok. `status`, `staff`, `isDeleted*` **değişemez**; dal `resource.data.status == 'active'` ister (askıdaki / silinmiş hesap profil düzenleyemez). Hesap silme ayrı daldır (aşağıda).
- **U (sahibi, hesap silme — T-29 `canMarkDeleted()`; `AccountDeletionRepository.markDeleted`, sözleşme `docs/plans/T-29.md` §4 a-1, b, g-1):** `status: active → deleted` **tek adımdır**, ara durum (`deleting`) yoktur ve dönüş yoktur — `deleted` belgede `status` hiçbir dalın beyaz listesinde değildir, `isSoftDelete` önceki `isDeleted == false` ister. Koşullar: `isOwner()`, `resource.data.status == 'active'` (askıdaki hesap silinemez), `isSoftDelete(['name','nameLower','bio','interests','avatarPath','department','year','status'])` (`deletedBy == uid()`, `deletedAt == request.time`), değerler `Anonymization.userPayload` ile **birebir** — `name == 'Silinmiş kullanıcı'` (`Anonymization.deletedUserName`; yerelleştirilmez, arayüz ARB `commonDeletedUser` gösterir), `nameLower == 'silinmiş kullanıcı'`, `bio == ''`, `interests == []`, `avatarPath` / `department` / `year` `null` ya da anahtarsız (W-51), `status == 'deleted'` (kısa biçim: `request.resource.data.status=='deleted' && name=='Silinmiş kullanıcı' && bio=='' && interests==[]` — `anonymization_test.dart` paritesi); **dokunulmaz:** `avatarSeed`, `staff`, `profileComplete`, `createdAt`. **Aynı batch bağı:** `getAfter(users/{uid}/private/account).data.email == ''` (boş e-posta yalnızca §3.2 anonimleştirme dalından gelebilir). 1 erişim yolu. Başkanlık engeli bu belgede **değil**, istemcidedir (`precheck`; kural kulüp bilmeden başkanlığı sorgulayamaz); engeli atlayan başkanın üyeliği M14'te `active` kalır ama anlık görüntüsü ve iletişimi boşalır (§3.4, T-29 güvenlik incelemesi). Silinmiş hesabın sahibine yalnızca temizlik dalları açıktır: M14 + contact U(c), vazgeçme (§3.8), engel / kayıt / bildirim soft delete (§3.9, §3.13, §3.14); yardımcılar `deletedUser()` = `emailOk() && get(users/uid()).data.status == 'deleted'` ve `notDeletedUser()` = `!exists(users/uid()) || me().status != 'deleted'` (§2).
- **U (süper admin):** yalnızca `status` (`active↔suspended`) (+`updatedAt`). Gerekçe bu belgeye **yazılmaz**: aynı batch'te `users/{uid}/private/account.suspendReason` güncellenir (§3.2, CD-133).
- **`suspendReason` bu belgenin alanı değildir** (CD-133): C ve U beyaz listelerinde yoktur; sahibi ya da süper admin bu anahtarı `users/{uid}`'e yazamaz (tablo dışı alan = ret).
- **D:** `false`.

### 3.2 `users/{uid}/private/account`
- **R/C/U:** `uid == request.auth.uid` && `emailOk()`; `email`/`emailLower` = `request.auth.token.email` (+lower); `fcmTokens` ≤ 10 eleman ve her eleman `{token: s 1–4096, platform: 'ios'|'android', updatedAt: timestamp}` (başka anahtar yok; `// limit: fcmTokenMax` — bozuk eleman süper adminin okumasını ayrıştırma hatasına düşürür, CD-133 madde 14). **C** ayrıca `existsAfter(users/{uid})`: hesap belgesi profil belgesi olmadan oluşturulamaz (§3.1 C ile karşılıklı). **R** ayrıca süper admin (ADM-05 e-posta araması: `collectionGroup('private')` + `emailLower` aralığı → **kural koleksiyon grubu için ayrıca yazılır**: `match /{path=**}/private/{doc} { allow read: if isSuper(); }`).
- **`suspendReason` (CD-133) sahibi için salt okunurdur:** C'de `request.resource.data.get('suspendReason', null) == null`; U (sahibi) `diff(resource.data).affectedKeys()` içinde `suspendReason` taşıyamaz (hesap silme dalı dahil). Alan null olabilir → `data.get('suspendReason', null)` ile okunur (W-51: istemci belgesinde anahtar yok, seed'de açık `null`).
- **Silinmiş hesap (T-29):** sahibin U dalına `notDeletedUser()` eklendi — anonimleştirilmiş e-posta token'dan geri yazılamaz, `fcmTokens` / `lastLoginAt` yazılamaz (D-29; askıdaki hesap yazmaya devam eder). `touchLastLogin` 1 erişim yolu okur.
- **U (sahibi, anonimleştirme — T-29 `canAnonymizeAccount()`; domain-model §11 adım 3):** `docId == 'account'`, `touches(['email','emailLower','fcmTokens'])`, `email == '' && emailLower == '' && fcmTokens == []` (`Anonymization.accountPayload`), `getAfter(users/{uid}).data.status == 'deleted'` (aynı batch'te — ya da daha önce — silinmiş profil: etkin hesap e-postasını boşaltıp ADM-05 aramasından kaybolamaz). `lastLoginAt`, `suspendReason`, `isDeleted*` değişmez; yeniden koşma (aynı değerler) geçer. Auth kimliği ve Auth e-postası kalır (Q-11). 1 erişim yolu.
- **U (süper admin):** `isSuper() && touches(['suspendReason'])` — yalnızca `suspendReason` (+`updatedAt == request.time`): `null` (etkinleştirme) ya da `is string && size() in 1..300` (`// limit: adminReasonMax`, CD-30). Belge yoksa yazılamaz (süper admin için C yok); `email`, `emailLower`, `fcmTokens`, `lastLoginAt`, `isDeleted*` değişemez.
- Okuyanlar: **sahibi** (kendi gerekçesi) ve **süper admin** (ADM-05); başka hiçbir bağlam (aynı kulübün yöneticisi dahil) okuyamaz. Durum–gerekçe tutarlılığı (`suspended` ⇒ dolu, `active` ⇒ `null`) Rules'ta belgeler arası zorlanmaz; `AdminRepository.suspendUser/activateUser` ikisini tek batch'te yazar (yalnızca süper admin yazabildiği için yönetsel risk, kabul).
- **D:** `false`.

### 3.3 `clubs/{clubId}`
- **R:** `emailOk()` && (`!resource.data.isDeleted` || `isSuper()`). Askıdaki kulüp okunur (kart "askıda" görünümü / yönetici paneli); listeden ayıklamak arayüzdedir. **T-15:** tekil okumada var olmayan kulüp boş döner (`resource == null`; "yok" ile "yetkisiz" ayrışır). Liste sorgusu `isDeleted == false` süzgecini taşır (§6). Kimlik listeli sorgu (`documentId in […]`, `getClubs`) belge belge değerlendirilir: listedeki silinmiş ya da var olmayan **tek** kimlik sorgunun tamamını düşürür (süper admin hariç) → `ClubRepository.getClubs` ret halinde kimlikleri tek tek okur, okunamayanı atlar (CD-137 madde 8k).
- **C:** yalnızca `isSuper()` (ADM-03). Alan beyaz listesi, `nameLower` = `name.lower()`, `memberCount == 1` ve **aynı batch'te** `memberships/{clubId}_{presidentId}` (role `president`, `active`) ve `presidentId` tutarlı (`getAfter(mPath(clubId, presidentId)).data.role == 'president'`); danışman girildiyse (G-1) ek `advisor` üyeliği (`memberCount`'a dahil değil). Ad benzersizliği: istemci `nameLower` sorgusuyla kontrol eder, Rules **ikinci savunma** olarak `clubs/{nameLower-index}` kullanmaz — benzersizlik ihlali yönetsel risktir (kabul; K-sorusu adayı).
- **U (yönetim `board|president`):** yalnızca `summary, about, conditions, social, approvalRequired, applicationsOpen, requireNote, palette, pattern, coverSeed, logoPath, coverPath, pinnedPostId`; sınırlar `Limits`. `name, nameLower, categoryId, iconName, founded, status, presidentId` **değişemez** (MGT-09'da kilitli).
- **U (süper admin):** `status, suspendReason` (zorunlu neden), `name/nameLower/categoryId/iconName/founded`, `presidentId` (+aynı batch üyelik tutarlılığı).
- **U (devir — başkan):** `presidentId` yalnızca başkanlık devri batch'inde: `getAfter` ile eski başkan `board`, yenisi `president` (domain-model §5).
- **U (sayaç):** `memberCount` yalnızca üyelik değişimiyle ±1 (§5). Yalnızca `memberCount` + `updatedAt` değişir; sonuç ≥ 0. **T-15 aktörü yalnızca üyeliğin sahibidir** (M2 / M3-`active` / M8): eşlik eden belge oturumdan türetilir (`memberships/{clubId}_{uid()}`), kural onun yazım-öncesi / yazım-sonrası durumunu okur: `+1` ⇒ sonra `active`, önce `active` değil; `−1` ⇒ `active → left`. **`lastMembershipRef` yazılmaz** (CD-137 madde 8q; CD-41'in `clubs` satırı kapatıldı): kulüp belgesi doğrulanmış herkese açıktır ve yol, kimin katıldığını / ayrıldığını üye olmayana sızdırıyordu (domain-model §3 `viewInside`, D-29) — alan beyaz listede yoktur, yazan sayaç yükü reddedilir. **T-29:** `−1` dalı ayrıca yazım-öncesi üyeliğin `role in ['member','board']` olmasını ister (ek yol yok) — danışman `memberCount` dışıdır, başkan ayrılamaz; hesap silme (M14) sahibin bu `−1` dalını kullanır. Yönetici ve süper admin aktörü (M5, M9, M12) T-30 / T-37'de eklenir; aktörün sahibi olmadığı dalda işaretçi herkese açık belgede **durmaz** (karar: W-64).
- **U (`pinnedPostId` dalı — T-19, sözleşme `docs/plans/T-19.md §6.a` madde 9–11):** yalnızca `pinnedPostId` + `updatedAt`, gönderi yazımıyla **aynı işlemde** ve değer gerçekten değişirken. Yeni değer doluysa: `activeUser() && isManager(clubId)`, kimlik `[A-Za-z0-9_-]+`, `getAfter(posts/yeni)` bu kulübün, `pinned == true`, silinmemiş. Eski değer doluysa `getAfter(posts/eski).pinned == false` (aynı anda iki sabit gönderi kalamaz; eski gönderi yoksa koşul aranmaz). Yeni değer `null` ise aktör yönetici **ya da** eski sabit gönderi bu işlemde siliniyor (`get(...).isDeleted == false && getAfter(...).isDeleted == true` — süper adminin moderasyon silmesi; yetkiyi gönderi kuralı doğrular). Karşılığı gönderideki `canTogglePin` / `canRemovePost` dallarıdır (§3.5). Yönetim alanlarının geri kalanı T-30 / T-36'da açılır.
- **D:** `false`.

### 3.4 `memberships/{clubId}_{userId}` ve `/private/contact`
Belge ID'si `clubId + '_' + userId` ile **birebir** eşleşmeli (`request.resource.id == resource/clubId_userId`).

- **R:** (a) `emailOk() && resource.data.userId == uid()`; (b) `seesMgmt(resource.data.clubId)` (doğrulanmış e-posta + aktif hesap — askıdaki yönetici başvuruları okuyamaz, CD-137 madde 8r); (c) üye listesi: `resource.data.status=='active' && seesInside(resource.data.clubId)` (sorgu `clubId` + `status=='active'` ile; askıdaki üye okur). `pending/rejected/removed/left/cancelled` belgeleri (c)'ye girmez. Üyelik belgesi **e-posta ve başvuru notu taşımaz** (domain-model §2.4; D-29, CD-137): ikisi de `/private/contact`'tadır. `note` üyelik belgesinin alanı **değildir** — C ve U beyaz listelerinde yoktur (`keys().hasOnly`); bu anahtarı taşıyan üyelik yazımı reddedilir.
  - **R (d) — yönetici görünürlüğü (T-17, CD-139):** `resource.data.status=='active' && resource.data.role in ['president','board','advisor'] && activeUser()` — kulübün etkin yöneticileri (başkan, yönetim kurulu, danışman) doğrulanmış ve **aktif** her kullanıcıya okunur (CLB-03 "Yönetim kurulu", `ClubCard` avatar grubu; `MembershipRepository.listManagers`). Sorgu `status=='active'` + `role in […]` (bu üç rolün alt kümesi) süzgeçlerini taşımalıdır; süzgeç eksilirse / genişlerse (sıradan üye, `pending`) sorgu reddedilir. Tam üye listesi (c) üyelere özel kalır; `/private/contact` bu daldan **etkilenmez** (kapalı). Doğrulanmamış, alan adı dışı, askıdaki ve profili eksik kullanıcı (d)'den okuyamaz.
- **`/private/contact`** — alanlar `email`, `emailLower`, `note` (başvuru notu, CD-137) + `BaseFields`; "sahibi" = üst üyelik belgesinin `userId == uid()` (okumada `get`, yazımda `getAfter`).
  - **R:** sahibi, `seesMgmt(clubId)` (danışman dahil; doğrulanmış e-posta + **aktif hesap** — askıdaki ya da doğrulanmamış jetonlu yönetici okuyamaz, CD-137 madde 8r), süper admin. ### 3.16 `announcementCounters/{clubId}_{yyyyMMdd}`

Beğeni, oy ve kayıt yolları oturumdan türer (işaretçi yok); oy sayacı alanı yoktur (`count()`).

Etkinlik sayaç dalı `touches([goingCount, waitlistCount, attendedCount])` + yazım-sonrası üçü `>= 0` ve `attendedCount <= goingCount`; Δgoing = +1 ⇒ `resource.get('capacity', null) == null || goingCount_sonra <= capacity` (kontenjan aşımı burada reddedilir; anahtarsız / null = sınırsız — W-51); `(+1,0,0)` kontenjanlıda ayrıca `waitlistCount == 0`; `(0,+1,0)` yalnızca kontenjanlıda, doluyken ya da bekleyen varken (CD-144 (10)). **Kendi dalı** `(+1,0,0)` yok|cancelled→going · `(0,+1,0)` yok|cancelled→waitlist · `(−1,0,0)` going→cancelled · `(0,−1,0)` waitlist→cancelled: eşlik eden kaydın yolu oturumdan türetilir (`rsvps/{eventId}_{uid()}`), `getAfter` + `exists`/`get` ile geçiş, `eventId` / `userId` alanları eşleşir. **Yönetici dalı** `(0,0,±1)` going↔attended · `(+1,−1,0)` waitlist→going (terfi; tek yazım): işaretçi aynı işlemde yazılan `events/{eventId}/private/counter` yan belgesindedir (`seesMgmt` okur), gösterdiği kaydın yolu kendi alanlarından yeniden kurulur, aktör `activeUser() && isManager(clubId)`. Katılım kuralı karşı yönden etkinliğin üç sayacının **işlemin tamamında** (`get` ↔ `getAfter`) tam beklenen kadar oynadığını görür (`eventCountersMoved`): sayaçsız kayıt, kayıtsız sayaç, ±1 dışı, çift sayım ve tek artışla iki kayıt reddedilir. Emülatörde aynı belgeye iki yazım tek yazım gibi değerlendirilir; işlemin tamamı denetimi bu birleşmeden bağımsızdır.

Kural: sayaç **hiçbir zaman** mutlak değer olarak serbest yazılmaz; her sayaç yazımı yukarıdaki eşlik eden yazımla birlikte ve tam ±1'dir. Sayaç bozulması (örn. elle düzeltme) süper admin betiğiyle (`tool/admin/`) yapılır, istemciyle değil.

## 5. Mod C bildirim fan-out sınırı

Mod C'de bir işlem çok alıcıya yazar (duyuru → tüm üyeler). Erişim çağrısı bütçesi nedeniyle fan-out **parçalı** yapılır (batch başına en çok N alıcı; kuralın alıcı başına `get` yapmaması şart). **T-25 ölçümü** (`firebase/test/budget/fanout_budget.test.js` → `fanout_result.json`): parçadaki her belge aynı 3 yolu okur (`users/{uid}`, üyelik, olay belgesi); emülatörde N ∈ {10 … 450} hepsi geçti → `Limits.notificationFanOutChunkSize = 225` (en büyük geçen N'nin yarısı; RP05). `application_received` alıcı başına ayrı batch'tir (parça 1). **Canlı ortam notu:** Firebase belgesi aynı belgeye yinelenen erişimin önbelleğe alınmasını garanti etmez ("may be cached") ve istek başına 1 000 ifade sınırı emülatörde ölçülmez; yarıya bölme bu payı karşılar, T-45'te yeniden değerlendirilir (canlıda parça reddedilirse yalnızca `Limits` küçülür, kural değişmez). Duyuru yayını: önce gönderi + sayaç batch'i (kritik), ardından bildirim parçaları (en iyi çaba; başarısız parça tekrar denenir, kullanıcıya hata göstermez). Mod F'de bu bölüm gereksizdir (Function yazar).

## 7. Storage Rules

```
service firebase.storage {
  match /b/{bucket}/o {
    match /users/{uid}/{file}        { allow read: if signedInVerified(); allow create: if request.auth.uid == uid && imageOk(); allow update, delete: if false; }
    match /clubs/{clubId}/{file}     { allow read: if signedInVerified(); allow create: if isManagerOf(clubId) && imageOk(); allow update, delete: if false; }
    match /posts/{postId}/{file}     { allow read: if signedInVerified(); allow create: if <Firestore post yazarı> && imageOk(); allow update, delete: if false; }
    match /support/{ticket}/{file}   { allow read: if isSuperAdmin(); allow create: if signedInVerified() && imageOk(); allow update, delete: if false; }
  }
}
function imageOk() { return request.resource.contentType.matches('image/.*') && request.resource.size < 5 * 1024 * 1024; }
```
- Dosya adı **benzersiz** (zaman damgası/UUID); mevcut dosya **üzerine yazılmaz** ve silinmez. Değiştirme = yeni dosya + Firestore yol alanı (`avatarPath` vb.) güncelleme (D-10, architecture §10).
- **Üzerine yazmayı `update: false` engellemez (T-14):** Storage'da `create` dosya içeriği yazımının tamamıdır (var olan yola yeniden yükleme dahil), `update` yalnızca üst veridir. Açılan her `create` kuralı `resource == null` (`isNewFile()`) ister. Uygulanan `users/` kuralı (yukarıdaki taslağın yerine geçer; tam metin `docs/PLAN.md §11.5`): `allow get: if signedInVerified(); allow list: if false; allow create: if signedInVerified() && request.auth.uid == uid && isNewFile() && imageOk() && fileNameOk(file) && noCustomMetadata() && accountActive();` — `imageOk()` yalnızca `image/(jpeg|png|webp)`, `fileNameOk` = `StoragePaths.fileNamePattern` + uzantı ↔ içerik türü.
- **Sunum üst verisi ve boş dosya (T-14 güvenlik incelemesi):** uygulanan `imageOk()` ayrıca `size > 0`, `contentEncoding == null || 'identity'` ve `contentDisposition == null || 'inline'` ister. Dosya silinemediği için (D-10) kötü yük kalıcı olurdu: `contentEncoding: gzip` küçük dosyayı indirirken GB'lara açtırır; `contentDisposition: attachment; filename=…` jetonlu indirme adresini keyfi adlı dosya dağıtımına çevirir. Özel üst veri beklemeyen yollar `noCustomMetadata()` çağırır (`posts/` `metadata.clubId` ister — CD-39). İstemci yalnızca `contentType` gönderir (parite: `parity.test.js`). **Sonraki yol açan task'lar (T-16/21/22/28) aynı `imageOk()`'i kullanır.**
- **Hesap durumu (T-14 güvenlik incelemesi):** `users/` yüklemesi `accountActive()` ister — `firestore.get(users/{uid}).data.status == 'active'` (yükleme başına 1 okuma; kuralın son koşulu). Mod C'de askı yalnızca `users.status`'tur, Auth hesabı açık kalır: bu okuma olmadan askıdaki / silinmiş hesap klasörüne dosya yığabilirdi. Belge yoksa ret (AUT-05'te `createProfile` yüklemeden önce koşar; `profileComplete` aranmaz). Okuma (`get`) askıdaki hesaba açık kalır. `support/` yolu T-28'de aynı denetimi alır.
- **`clubs/` (T-16 — yalnızca okuma):** uygulanan kural `allow get: if signedInVerified(); allow list: if false; allow create: if false;` — kulüp logosu / kapağı doğrulanmış her kullanıcıya tek dosya olarak açıktır (kulüp belgesi de öyledir; CLB-01, CLB-03); klasör listesi kapalıdır (eski görseller silinmez, D-10 — `users/` ile aynı gerekçe). Yükleme (`isManagerOf(clubId) || isSuperAdmin()` + `users/` kalıbı) kulüp ayarlarıyla birlikte **T-36**'da açılır.
- **`posts/` (T-21, CD-39):** uygulanan kural (yukarıdaki taslağın yerine geçer) `allow get: if signedInVerified(); allow list: if false; allow create: if signedInVerified() && isNewFile() && imageOk() && fileNameOk(file) && postId.matches('[A-Za-z0-9_-]+') && clubMetadataOnly() && isManagerOf(request.resource.metadata.clubId) && accountActive();`
  - **Yükleme:** yalnızca `metadata.clubId` kulübünün **etkin yöneticisi** (üyelik `active` + rol `board` / `president` — Firestore `isManager(c)` ile aynı). Danışman, üye, başvurusu bekleyen / ayrılmış kullanıcı, başka kulübün yöneticisi ve **süper admin** yükleyemez (gönderiyi yalnızca kulüp yönetimi yayınlar). `isManagerOf(clubId)` = `firestore.get(memberships/{clubId}_{uid})` (kimlik `FirestoreIds.membership`; uid oturumdan, üst veriden değil); belge yoksa ret. Kimlik birleşimi tek başına belirsiz olduğundan (`c01_u` + `x` = `c01` + `u_x`) okunan belgenin `userId == uid` ve `clubId == metadata.clubId` alanları da eşleşmelidir.
  - **Üst veri:** `clubMetadataOnly()` — özel üst veri yalnızca `clubId` ve `uploaderId` taşır (+ `firebaseStorageDownloadTokens` toleransı, `noCustomMetadata()` ile aynı gerekçe). `clubId` `[A-Za-z0-9_-]+` desenindedir (belge yoluna gömülür: `/`, `..`, boş değer başka bir belgeyi gösteremez); `uploaderId` oturumdaki uid'dir (aşağıda "Yükleyen izi"). İstemci `PostRepository.uploadImages` `customMetadata: {'clubId': clubId, 'uploaderId': uploaderId}` gönderir (parite: `parity.test.js`).
  - **Gönderi belgesi aranmaz:** yükleme anında `posts/{postId}` yoktur (K-18: önce görseller, sonra gönderi; `postId` = `newPostId()`). Yolun gönderiye ait olduğunu Firestore `posts` C / U kuralı denetler (`images[i].path` = `posts/{postId}/` + `StoragePaths.fileNamePattern`); Firestore yalnızca yol **desenine** bakar: dosyanın varlığını, yükleyenini ve `metadata.clubId` değerini denetlemez. Bu yüzden başka kulübün yöneticisi **kendi kulübü adına** bu klasöre dosya yükleyebilir (kabul edilen davranış; `storage.test.js` "başkasının gönderi klasörü"), ama yükleyen dosyayı gönderiye **iliştiremez** — `posts.images` alanını yalnızca gönderinin yazarı (hâlâ yöneticiyken) yazar; yazar klasördeki başka bir dosyanın ya da var olmayan bir dosyanın yolunu yazabilir. Sonuç yetki yükseltme değil, yetim dosyadır (liste kapalı, üzerine yazma yok).
  - **Yükleyen izi ve klasör adı (T-21 güvenlik incelemesi):** özel üst veri yalnızca `clubId` + `uploaderId` (+ indirme jetonu) taşır ve `metadata.uploaderId == request.auth.uid` olmalıdır (alan atlanamaz, başkasının kimliği yazılamaz; üst veri sonradan değiştirilemez). Storage nesnesi yükleyeni kendiliğinden kaydetmez ve klasör adı kimlik taşımaz (`users/` yolunda klasör = uid): bu alan olmadan dosya yığan yöneticinin kim olduğu konsoldan bulunamaz, tek fren olan hesap askısı (§9.8) uygulanamazdı. Klasör adı `postId` belge kimliği desenindedir (`[A-Za-z0-9_-]+` — Firestore `posts` C kuralıyla aynı): keyfi adlı klasör açılamaz. İstemci: `FirebasePostRepository.uploadImages(…, clubId:, uploaderId:)` (parite: `parity.test.js`).
  - **Okuma:** doğrulanmış her kullanıcı, tek dosya (`get`); **üyelik aranmaz**. Yol yalnızca gönderi belgesinde durur (onu kulübün içini gören okur), dosya adı tahmin edilemez (64 bit rastgele) ve klasör listelenemez. Üyelik denetimi görsel başına bir Firestore okuması olurdu; indirme adresi jetonu zaten kuralları atlar. Ayrılan / çıkarılan üye bildiği yolu okumayı sürdürebilir (kabul edilmiş sınırlama §9.11).

## 9. Kabul edilmiş sınırlamalar (kullanıcıya bir kez bildirilir, `docs/PLAN.md` "Riskler"e yazılır)

1. **Profil okuma:** `users/{uid}` tüm doğrulanmış kullanıcılarca okunabilir; "ortak kulüp yoksa gizle" yalnızca arayüzdedir (D-29). Bu yüzden e-posta (D-29) ve askı gerekçesi (CD-133) bu belgede tutulmaz; ikisi de `users/{uid}/private/account`'tadır. `users.status` (askıda olduğu bilgisi) ise açık kalır: `activeUser()` ve arayüz bu alana bakar.
2. **Oy anonimliği:** oy belgeleri üyelerce okunabilir; arayüz kimin ne oy verdiğini göstermez.
3. **Mod C fan-out:** alıcının üyeliği Rules'ta doğrulanmaz; kötü niyetli bir **yönetici** başka kullanıcılara bildirim yazabilir (spam). Mod F'de yok. **K-J: kabul (CD-65)** — bildirim `create` kota kuralı yazılmaz; PLAN §20 R-07 + T-45 "Mod C spam sınırlaması raporu". T-25 Rules frenleri: üretici kulübün etkin yöneticisidir ve bildirim gerçek bir olaya bağlıdır (bildirimli duyurunun yazarı / yayındaki ya da iptal edilmiş etkinlik / aynı batch'teki terfi); bekleyen başvuran yalnızca o kulübün etkin yönetim kurulu / başkanına, **başvuru başına yönetici başına en çok bir** `application_received` yazabilir (kimlik `priorCount`'a bağlı — CD-148; kalan: iptal → yeniden başvuru döngüsü her turda bir belge, tur başvuru listesinde ve günlükte görünür — T-45 spam raporu). Tek seferlik olaylar (duyuru, iptal) yeniden itilemez; `event_new` yalnızca yayından sonraki 10 dk'lık pencerede; askıdaki / silinmiş kulübün yöneticisi bildirim yazamaz. Belgede metin yoktur (içerik enjeksiyonu yok); alıcı kendi kopyasını soft delete edebilir.
4. **Kulüp adı benzersizliği** istemci kontrolüne dayanır (yarış durumu mümkün, süper admin tek kişi → pratikte düşük risk).
5. **Askıdaki kulübün etkinlikleri** listede Rules'la değil istemciyle gizlenir (kural per-belge `get` yapamaz).
6. **Silinmiş-anonim kullanıcı** belgeleri ve içerikleri kalıcıdır (soft delete politikası); KVKK "silme" talebi için kalıcı temizlik süreci kullanıcıyla ayrıca netleştirilir (Q-11).
7. Zorunlu güncelleme/bakım (Remote Config) Rules'tan bağımsızdır; eski istemci Rules'a takılırsa DLG-26.
8. **Storage kotası (T-14):** Storage'da kullanıcı başına adet ya da toplam boyut kotası yoktur. Etkin bir hesap kendi klasörüne sınırsız sayıda (< 5 MB) görsel yükleyebilir ve dosyalar silinemez (D-10). Frenler: dosya başına tür / boyut / üst veri sınırı (`imageOk()`), yalnızca kendi klasörü ve **askı** (`accountActive()`: askıdaki / silinmiş hesap yükleyemez). Kalıcı temizlik konsoldandır (madde 6 ile aynı süreç); App Check önerilir (CD-64).
9. **Hesap sayımı ve e-posta gönderim sınırı (T-14):** (a) AUT-04 hesabın varlığını sızdırmaz, ama AUT-02 kayıtlı adresi tasarım gereği söyler (`authErrExists`); konsolda *Email enumeration protection* kapalıysa Auth REST uçları da söyler. (b) Alan adı denetimi (D-27), 60 sn yeniden gönderme beklemesi ve giriş kilidi **yalnızca istemcidedir** ve bellekte tutulur (sıfırlama beklemesi ekran yeniden açılınca, doğrulama beklemesi uygulama yeniden başlayınca sıfırlanır); doğrudan REST çağrısı hepsini atlar. Senaryo: saldırgan REST ile başkasının okul adresine hesap açar (posta kutusu kanıtı gerekmez) ve doğrulama e-postasını döngüyle ister → kurbana spam, günlük e-posta kotası biter, yeni öğrenciler doğrulayamaz. Tek sunucu sınırı Firebase Auth kotalarıdır. Doğrulanmamış hesap hiçbir veriye erişemez (`emailOk()`). Önlem süreçtedir: T-46 konsol listesi (*Email enumeration protection* açık, Auth kota uyarısı), T-45 raporu, App Check önerisi (CD-64); Mod F'de `beforeCreate` engelleme işlevi.
10. **Gizlenen sabit gönderi (T-19, CD-141 madde 11):** gizleme (`hide`) sabitlemeye dokunmaz — `clubs.pinnedPostId` gizlenen gönderiyi göstermeye devam eder (işaretçi rastgele kimliktir, içerik taşımaz). Üye o gönderiyi okuyamaz (`permission-denied`); akış bu sonucu "sabit gönderi yok" sayar (W-70, T-20) ve kulüp yönetimi `unpin` ile işaretçiyi temizler. Gizlemenin aynı işlemde sabitlemeyi kaldırması T-37 şikayet çözümünde yeniden değerlendirilir.
11. **Gönderi görselleri (T-21):** (a) `posts/` görsel okuması üyelik aramaz — yolu bilen doğrulanmış her kullanıcı (ör. kulüpten ayrılmış üye) dosyayı okuyabilir; yol yalnızca gönderi belgesindedir, dosya adı tahmin edilemez, klasör listelenemez. (b) Storage kuralı kulübün durumunu okuyamaz (çapraz servis sınırı: 2 belge — §7): askıdaki / silinmiş kulübün yöneticisi `posts/` klasörüne dosya yükleyebilir; gönderi yazımı Firestore'da reddedildiği için dosya hiçbir gönderiye bağlanamaz (yetim dosya; fren = hesabın askıya alınması, §9.8). (c) Düzenlemeyle gönderiden çıkarılan görselin dosyası silinmez (D-10); yolu bilen okumayı sürdürür. (d) **Gizlenen (`isHidden`) ya da silinen gönderinin görseli de silinmez ve okunmaya devam eder:** yolu bilen doğrulanmış her kullanıcı `get` ile okur; daha önce alınmış jetonlu indirme adresi oturumsuz ve süresiz çalışır (kuralları atlar). Moderasyon gizlemesi gönderiyi akıştan kaldırır, **zararlı görseli Storage'dan kaldırmaz** — bunun için süper admin konsoldan nesneyi siler ya da indirme jetonunu iptal eder (uygulama dışı yordam; W-74 → T-37 / T-46). Yükleyen `metadata.uploaderId` alanından bulunur. (e) Kural beyan edilen içerik türüne güvenir ve **piksel boyutunu göremez**: 5 MB altındaki dosya çok büyük pikselli olabilir. İstemci gönderi görselini `BoundedImage` ile çözer (piksel sayısı `MediaConstants.imageSourceMaxPixels` üstü → çözülmeden ret, yer tutucu; kalanı uzun kenar ≤ 1 600 px) — düşük bellekli cihazda doğrulama W-75. (f) `imageOk()` `cacheControl` alanına bakmaz (`public, max-age=…, immutable` kabul edilir): koşul, canlıda sunucu varsayılanı görülmeden eklenmez (T-14 dersi; W-74). (g) Başka kulübün yöneticisi kendi kulübü adına herhangi bir `posts/{postId}/` klasörüne dosya yükleyebilir (§7); iliştiremez, dosya yetim kalır, izi `uploaderId`'dir.

12. **Etkinlik ve katılım (T-22 — sözleşme §6.10 madde 12; güvenlik incelemesi CD-144 (10)):** (a) ~~vazgeçme bittikten sonra serbest~~ → kapatıldı (`endsAt > request.time`); (b) ~~boşalan yere sıra atlanarak girilir~~ → kapatıldı (bekleyen varken `going` yok); (f) bilet kodu tekilliği Rules'ta kurulamaz (kodu istemci üretir): kopyalanmış kod yönetim aramasında belirsiz eşleşmedir (W-79); (c) K-F harfiyen `goingCount == 0`: yayından çekilen (ve sonra silinen) taslakta bekleme kayıtları kalır; (d) `members` etkinliğinin ve taslağın kapak görseli Storage'da üyelik aramadan okunur (yolu bilen; §7 `events/`); (e) yönetici dallarında (yoklama, terfi) `clubLive` aranmaz — askıdaki kulübün süren etkinliğinde yoklama alınabilir.

13. **Destek talebi ve `support/` eki kotası yok (T-28 — güvenlik incelemesi, CD-151 (7)):** `supportTickets` create'inde talep sayısı ya da bekleme süresi sınırı yoktur; talep numarasını istemci seçtiği için Rules rastgeleliği de zorlayamaz. `support/` yüklemesinde §9.8'deki "yalnızca kendi klasörü" freni yoktur: etkin her hesap desene uyan her `support/{ticketNo}/` klasörüne dosya yükleyebilir (iliştiremez; yetim dosya, izi `metadata.uploaderId`). Senaryo: etkin bir hesap betikle binlerce 500 karakterlik talep ve her biri < 5 MB silinemeyen (D-10) ek üretir; süper adminin süzgeçsiz listesi şişer. Frenler: askı (`activeUser()` / `accountActive()` — askıya alınan hesap yeni talep açamaz ve ek yükleyemez; testli), her talepte `userId`, her ekte `uploaderId` (kimlik izi), App Check önerisi (CD-64), süper admin listesinde `limit` (§6), T-45 spam raporu. Kalıcı temizlik konsoldandır (madde 6 / 8 ile aynı süreç). Bekleme kuralı (ör. `users/{uid}/private/account.lastTicketNo` + `lastTicketAt` işaretçisi, aynı batch'te `getAfter`) gerekirse T-45'te yeniden değerlendirilir (W-88). PLAN §20 R-27.

14. **Hesap silme (T-29 — sözleşme `docs/plans/T-29.md` §4 b, c):** (a) dizi tek batch değildir (adım 1 `markDeleted` → parçalar): adım 1 kesinleştikten sonra kesilen dizi silinmiş hesapta kalan işlerle durur; bir sonraki girişte `resumeCleanup` güncel durumdan sürer (en iyi çaba). Hesap `deleted` olduktan sonra yalnızca temizlik dalları açık olduğu için arada yeni kişisel veri oluşmaz. (b) **Başkanlık engeli istemcidedir** (`precheck`; Rules M14 başkanı yalnızca `left` yapmaz): değiştirilmiş istemci ya da ön denetim sonrası devir alma yarışında başkan hesabı `deleted` olabilir; başkan üyeliği `active` kalır, anlık görüntüsü ve `private/contact`'ı yine boşalır (M14 başkan dalı). Kulübün başkanı "Silinmiş kullanıcı" görünür; silinmiş hesap geçerli jetonuyla o kulübün içini (`seesInside`) okuyabilir ama yazamaz — kulüp süper admin / devir akışıyla düzeltilir (W-90: T-33 / T-37; devir hedefi etkin hesap olmalı — W-89, T-30). (c) Silinmiş hesap temizlenen bildirimlerini **geri alamaz** (`notifications` U (3) `notDeletedUser()` — T-29 güvenlik incelemesi); okundu işareti ve soft delete açık kalır (yalnızca kendi gelen kutusu). (d) Auth kimliği, Auth e-postası ve Storage avatar dosyası kalır (Q-11, D-10); kalıcı temizlik uygulama dışıdır (madde 6). (e) Temizlik **en iyi çabadır**: parçalar bağımsızdır (geçici hata `RetryPolicy`, kalıcı hata veren parça öğe öğe, başarısız parça diziyi durdurmaz); etkinliği okunamayan açık kayıt (ayrılınan kulübün üyelere özel etkinliği) etkinlik okunmadan vazgeçilir (`cancelUnreadableRsvp`; `canCancelRsvp` okuma izni istemez, bitmişse reddeder — W-80). Hiç dönmeyen kullanıcının yarım kalan temizliği yönetici betiğiyle tamamlanır (W-91, T-37); yarım temizlikte kalan bekleyen başvurunun onayı T-30'da reddedilir (W-89).
